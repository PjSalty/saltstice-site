Open a SOPS file, see a `sops:` block at the bottom and a wall of `ENC[AES256_GCM,...]` values, and you'll conclude it's encrypted. That conclusion doesn't follow. SOPS encrypts the values whose KEY NAMES match `encrypted_regex`. Anything else is written straight through, in the clear, in the same file, and the file still validates.

Here's the shape of the rule doing it:

```yaml
creation_rules:
  - path_regex: ^credentials\.sops\.yaml$
    encrypted_regex: ^(.*(pass|psk|token|secret|key|hash).*)$
    age: age1...
```

That's a denylist expressed as a name pattern. It catches `admin_password` and `api_token` and `client_secret`. It does not catch a key called `acmedns_credentials`, or `seaweedfs_s3_config`, or `keepalived_auth_pass` if `pass` isn't in your alternation yet. Those keys hold secrets. The regex doesn't know that, because it's matching the name, not the thing.

Two properties make this hard to spot by eye:

- The file is mostly encrypted. A hundred-odd `ENC[` values and eight cleartext ones looks like an encrypted file at a glance, and it survives `sops filestatus` reporting `{"encrypted":true}`, because the file IS encrypted, just not all of it.
- The regex applies at WRITE time. Widen it later and nothing re-encrypts. A value written in the clear in March is still in the clear today, and every later edit to other keys leaves it exactly where it is.

## Checking it without reading the secrets

You don't want to decrypt the whole file to audit this. That puts every value in your terminal, your scrollback, and your shell history. Walk the YAML and print key PATHS only:

```python
import sys, yaml
d = yaml.safe_load(sys.stdin)
plain, enc = [], 0

def walk(n, path):
    global enc
    if isinstance(n, dict):
        for k, v in n.items():
            if k == "sops":       # skip SOPS's own metadata block
                continue
            walk(v, path + [str(k)])
    elif isinstance(n, list):
        for i, v in enumerate(n):
            walk(v, path + ["[%d]" % i])
    elif isinstance(n, str):
        if n.startswith("ENC[AES256_GCM"):
            enc += 1
        else:
            plain.append(".".join(path))

walk(d, [])
print("encrypted: %d" % enc)
print("CLEARTEXT: %d" % len(plain))
for p in plain:
    print("   ", p)
```

It never prints a value. Run it against the file and against old revisions:

```bash
python3 keyscan.py < credentials.sops.yaml
git show <commit>:credentials.sops.yaml | python3 keyscan.py
```

Expect a couple of legitimate hits. A certificate's public half and a cloud region name came back cleartext here and both should be. What you're looking for is the name that makes you go "wait, that one".

## Fixing one without ever seeing it

If you find a cleartext value you can't re-encrypt it in place without reading it first. But you shouldn't keep it anyway. It's been sitting in git in the clear, so it wants rotating. Do both at once:

```bash
sops set credentials.sops.yaml '["kubernetes"]["app"]["admin_token"]' \
  "\"$(openssl rand -hex 32)\""
```

The new value is generated by command substitution and consumed in the same expansion, so it never lands in a prompt, a file, or your history. `sops set` writes through the current `encrypted_regex`, so as long as you widened the pattern first, the value goes in encrypted. Rotation and encryption in one move, and nothing is ever decrypted.

Then verify with the scanner above, not by eye.

## The backup file that carries it into git

Second half of this, and it's the half that actually publishes the problem. Credential tooling likes to write a timestamped backup before it changes anything. Mine did this:

```go
backupPath := filepath.Join(
    filepath.Dir(secretsPath),
    fmt.Sprintf("credentials.sops.yaml.backup.%s", time.Now().Format("20060102-150405")),
)
```

`filepath.Dir(secretsPath)` is the secrets repo root. So every rotation dropped an untracked file into a git working tree, and a routine `git add -A` swept them in. Twelve landed in one commit.

Write backups outside the working tree. Not gitignored, outside:

```go
base := os.Getenv("XDG_STATE_HOME")
if base == "" {
    home, err := os.UserHomeDir()
    if err != nil {
        return "", err
    }
    base = filepath.Join(home, ".local", "state")
}
dir := filepath.Join(base, "yourtool", "credential-backups")
if err := os.MkdirAll(dir, 0o700); err != nil {
    return "", err
}
```

Add the gitignore entry too, but treat it as the second layer. It only protects repos that happen to have it.

## Making the scanner useful on a secrets repo

The usual reason people don't run secret scanning on a secrets repo is that SOPS ciphertext is high-entropy base64 and trips every generic API key rule. The fix isn't to skip the repo or allowlist the file, it's to allowlist the ciphertext:

```toml
[[allowlists]]
description = "SOPS-encrypted values"
regexTarget = "line"
regexes = ['''ENC\[AES256_GCM''']
```

`regexTarget = "line"` is doing the work. The default target tests only the captured secret substring, which for a SOPS value can be the inner base64 without the `ENC[` prefix, so the pattern would never match. Testing the whole source line means any line carrying an `ENC[` blob is ignored.

Don't use a path-based allowlist here. That suppresses the whole file, which also hides the value somebody forgot to encrypt, and that value is the entire reason you're scanning this repo.

The nice side effect is that findings become trustworthy. Once ciphertext can't produce a hit, every hit in a `.sops.yaml` is a value that isn't encrypted. No triage, no "probably just SOPS noise". If it fires, it's real, and you can act on it without a debate.

One more: make sure the scan isn't stage-gated behind an earlier job. On a scheduled pipeline where an earlier stage skips by its own rules, a stage-gated scan skips too, and a skipped scan looks exactly like a clean one. Give it `needs: []` so it starts immediately.
